# Task4: Повышение надёжности приложения

Эта директория содержит файлы конфигурации NGINX, используемые для демонстрации и реализации механизмов повышения надёжности приложения: **Rate Limiting** и **Circuit Breaker**.

## Структура

- `nginx-rate-limiter.conf` — Конфигурационный файл NGINX для настройки ограничения частоты запросов (Rate Limiter) с разными лимитами для веб- и мобильного приложений.
- `nginx-circuit-breaker.conf` — Конфигурационный файл NGINX для настройки паттерна Circuit Breaker при взаимодействии с внешними сервисами (например, логистикой).

## Описание

В рамках задания были реализованы два аспекта надёжности:

### 1. Настройка Rate Limiter

**Цель:** Настроить разные лимиты на количество запросов в секунду с одного IP-адреса для веб- и мобильного приложений.

**Решение:**

*   Используются директивы `limit_req_zone` для создания **двух отдельных зон** лимита: `rl_web` (50r/s) и `rl_mobile` (30r/s).
*   С помощью директив `if` и переменной `$http_client_type` (предполагается, что клиенты передают заголовок `Client-Type: web` или `Client-Type: mobile`) определяется, к какому типу клиентов относится запрос.
*   В зависимости от типа клиента применяется соответствующий лимит с помощью директивы `limit_req`.

### 2. Настройка Circuit Breaker

**Цель:** Повысить надёжность при взаимодействии с внешними сервисами, изолируя клиента от проблем внешнего сервиса (например, медленного ответа или недоступности).

**Решение:**

*   В блоке `upstream` для внешнего сервиса (`logistics.company.com`) установлены параметры `max_fails=5` и `fail_timeout=30s`. Это означает, что если 5 подряд запросов завершатся ошибкой, сервер будет помечен как недоступный на 30 секунд.
*   Установлены таймауты `proxy_connect_timeout`, `proxy_send_timeout`, `proxy_read_timeout` на **3 секунды**, чтобы избежать долгого ожидания ответа.
*   Директива `proxy_next_upstream` отключена (`off`), чтобы не пытаться повторно отправлять запрос к другому серверу (в данном случае, он один).
*   Директива `proxy_intercept_errors` включена, чтобы включить перехват ошибок от upstream-сервера.
*   В `location /logistics/` используется директива `error_page`, которая перенаправляет определённые HTTP-ошибки (500, 502, 503, 504) на внутренний `location @logistics_fallback`.
*   `location @logistics_fallback` возвращает **контролируемый JSON-ответ** с кодом 503 "Service Unavailable", когда основной сервис недоступен или отвечает с ошибкой.
