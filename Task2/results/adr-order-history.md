# ADR: История покупок

### **Автор: Алексей Тимофеев**

### **Дата: 2025-12-17**

## Функциональные требования

| **№**  | **Действующие лица или системы**   | **Use Case**   | **Описание **                                                                                                          |
|:------:|:-----------------------------------|:---------------|:-----------------------------------------------------------------------------------------------------------------------|
|   1    | Пользователь                       | Список заказов | Просмотреть все свои заказы с датой, суммой, способом доставки и финальным статусом. Поддержка пагинации и сортировки. |
|   2    | Пользователь                       | Детали заказа  | Посмотреть состав заказа: товары, количество, цены, итоговая сумма, способ оплаты и доставки, финальный статус.        |
|   3    | Пользователь → Invoice             | Скачать чек    | В карточке заказа получить и открыть/скачать PDF-файл чека по временной ссылке (pre-signed URL) из S3.                 |
|   4    | Пользователь → Review              | Оставить отзыв | Написать и отправить отзыв на товар, купленный в этом заказе.                                                          |
|   5    | Пользователь → Cart                | Заказать снова | Перенести все товары из этого заказа в текущую корзину для быстрого повторного заказа.                                 |


### **Нефункциональные требования**

| **№** | **Требование**                                                                                                                           |
|:-----:|:-----------------------------------------------------------------------------------------------------------------------------------------|
|   1   | 95% запросов: загрузка списка заказов — не более 300 мс, карточки заказа — не более 400 мс (при стабильной работе системы).              |
|   2   | Eventual consistency: данные в истории могут обновляться с небольшой задержкой (до 5 секунд), но в итоге всегда будут актуальными.       |
|   3   | Graceful degradation: Чтение данных доступно 99.9% времени. Если не работают отзывы, корзина или счёт — основной функционал не ломается. |
|   4   | Безопасность: Пользователи видят только свои данные. Проверка происходит через токен (JWT) и по ID пользователя.                         |
|   5   | Наблюдаемость: Система собирает метрики, логи и трассировки (traceId/spanId) для диагностики и отслеживания проблем.                     |

## Решение

Применяются паттерны **CQRS** и **API Composition**:

- Вводится  **Order History Query Service** — отдельный сервис для чтения истории заказов.
- Он хранит **упрощённые данные**, подходящие для отображения: название товара, цена, статус и т. д.
- Все изменения происходят в **Order Service** — сервисе записи. Он работает через события.
- Если нужно больше информации (например, отзывы), используется **API Composition** — сервис чтения обращается к другим сервисам (например, Review Service).

**Компоненты C2:**

- **API Gateway** → **BFF (Mobile)** — точка входа для мобильного приложения: авторизация, кэширование, пагинация.
- **Order History Query Service** + **PostgreSQL** — хранит и отдаёт список и детали заказов.
- **Kafka** — шина событий, через которую сервисы обмениваются информацией. 
События генерируются **Order**, **Payment**, **Delivery** и надёжно передаются в Kafka с помощью паттерна **Outbox** + **Change Data Capture**.
- **Order History Query Service** получает события и обновляет модель для чтения, обеспечивая согласованность и идемпотентность обработки.
- **Invoice Service + S3** — предоставляет PDF-чек по временной ссылке (pre-signed URL).
- **Review Service** — оставить или посмотреть отзыв.
- **Cart Service** — заказать снова.
- **Auth Service** —  проверка токенов (JWT).

## Обоснование

- История заказов быстро отображается, потому что данные уже подготовлены и хранятся отдельно.
- Статусы и итоги обновляются автоматически через события из других сервисов (оплата, доставка).
- Дополнительные действия (чек, отзывы) работают отдельно и не влияют на скорость основного экрана.

## Альтернативы

1) **API Composition (без read‑модели)**  
   Плюсы: простота запуска, отсутствие дублирования данных.
   Минусы: сложная сборка данных из нескольких источников, высокая нагрузка на сервисы, сильная связанность, риск несоответствия нефункциональным требованиям.

2) **Event Sourcing**  
   Плюсы: полная история изменений по каждому заказу.
   Минусы: повышенная сложность реализации, необходимость собирать модель чтения из событий, избыточность для данной задачи.

## Недостатки, ограничения, риски

- **Eventual consistency**: задержка обновления данных до 1–5 секунд (может быть критичной для бизнеса).
- Сложность управления схемами событий и их версиями.
- Дублирование данных в read-модели: дополнительные расходы на хранение и синхронизацию.
